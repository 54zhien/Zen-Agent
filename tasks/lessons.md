## 2026-09-20 · `inc5-review-debt`（E：单事务 CAS + edit revision）

### 1. 注释承诺了实现没有提供的东西，是缺陷，不是文档问题

`PersistenceStore+ProviderInstances.swift` 原文：

> it has to be impossible to change an instance without changing what a frozen run
> compares against

而两个并发编辑者都读到 revision N、都写 N+1，这句不成立。

**规则**：注释里写下的不变量，必须有**一条能红的测试**或**一个数据库约束**在背后。
写不出守卫的，就不要写成不变量 —— 那种句子比没有注释更糟，因为它让读者停止怀疑。
审查时优先找这一类：**断言越强、背后越空**的注释。

### 2. 「读一次、传播下去」比「读两次、希望一致」便宜

同一份事实被读两次，中间就可能变。E 的原始形态（B）就是这样：窗口和 phase
分两次加锁读，报出的措辞与窗口可能不一致。

**规则**：一个事实只读一次，把它**传**给需要它的地方。不允许用重试读、
二次判定来掩盖。读到之后立刻绑定成不可变值。

### 3. 签名里没有的位置，就不是可陈述的事实

探针测试 `attachCredential` 的「陈旧快照」时，我以为它会红，它**没有**。
原因：旧 API **不接受调用方的快照**，mutation 在内部重新读一次，
所以「基于陈旧快照的写入」在旧代码里根本无法表达。

**规则**：写回归测试前先问「**这个缺陷在当前 API 下能不能被表达**」。
不能，说明修法必须是 API 变更 —— 而且这本身就是该变更的理由。
反过来，一条「修复前也绿」的测试不要当成探针留下，要说明它只是守卫。

### 4. 探针要单独提交，红了再修

本机没有 Swift 工具链（CI 跑 macOS），红只能从 CI 看到。
`63f0867`（测试，预期红）→ `7bce7f5`（修复，绿）两段提交，
CI `35500976001` failure → `35501448459` success。

**规则**：允许**故意**提交一个红的探针提交，只要 commit message 说清「这是预期红、
为什么」。它把「修复值得这个 diff」变成可核对的事实，而不是自我声明。
代价是一次 CI 周期，比事后争论便宜。

### 5. fail-loud 要连**溢出**一起 fail-loud

把 `Int(rawValue) ?? 0` 改成抛出之后，`rawValue + 1` 仍然会在范围顶部**直接 trap**。
trap 不是 typed refusal —— 它杀掉进程，而触发它的正是这次改动自己点名的威胁模型
（手改 / 坏导入的库）。

**规则**：把一处静默回退改成 fail-loud 时，检查**同一表达式里剩下的算子**
在边界上是什么行为。`+ 1`、`Int(...)`、`String(...)` 各有各的边界。

### 6. `DatabaseQueue` 的「单次调用」不等于「一个事务」

两次独立的 `database.write` 是**两个**事务，中间那段窗口是真实的。
E 的机制就在那里，不是可选的优化。

**规则**：读-改-写要收敛进**同一个** `write` 闭包。跨两次调用做
「先读、再判断、再写」，无论中间隔多少行代码，都是竞态。

### 7. 自己引入的缺陷，不要靠「CI 已经绿了」放过

`7bce7f5` CI 已经是 success。但 `/code-review` 之后的复核查出两条**本轮自己引入**的
缺陷（create 路径原样写调用方的 revision；计数器溢出 trap）。

**规则**：绿只说明**已有断言**通过，不说明没写下的断言也成立。
审查发现的问题，即使 CI 全绿也要修 —— 「CI 绿」和「正确」是两个命题。

### 8. 「不破坏现有测试」要先 grep 全量调用点，不只规格点名的文件

P3 S1-9 的规格说「现有 ConversationDeletionTests 里的正路测试不能被破坏」，
并照字面检查了该文件。但 `/code-review` 五个角度独立命中同一个事实：
`IndeterminateTombstoneTests.finalizeIsIdempotent`（另一个文件）对同一
conversation 调两次 `finalizeDeletion` 并断言不抛——按规格字面实现的守卫
（非 pendingDeletion 一律抛）会打破这条文档化的幂等契约，CI 必然红。

**规则**：改一个方法前 `grep -rn "<方法名>" Tests/` 找**所有**调用点。
规格作者可能只读过点名的那几个文件；「按字面实现会红」的证据是 grep 出来的，
不是规格里写明的。

### 9. 修复 commit 本身必须预期绿；自查发现的打破要 amend，不叠加新 commit

print-mode 下探针 commit 可以故意红（lessons #4），但**修复 commit 必须是
预期绿**的状态。若 /code-review 自查发现某个已提交未推送的修复 commit
会打破既有测试（如 S1-9 的幂等冲突），要 `reset --soft` + 重放提交序列
把修正编入原 commit —— 而不是把「红修复 + 补丁修复」两个 commit 都推上去。
编排者按 commit 顺序核对红绿，红中间态会让账目失真。

**规则**：推出去的每个 commit 都要处于其 message 宣称的状态；
「预期的红」只能出现在探针 commit 里。
